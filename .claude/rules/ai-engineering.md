# AI Engineering Instructions

These instructions define the baseline engineering expectations for this
repository. This file is generated by the AI Engineering Framework installer
and is replaced on framework updates. Do not edit it directly.

Repository-specific instructions belong in `CLAUDE.md`. Project-specific
knowledge belongs under `.ai/`.

Project-specific architecture, business rules, persistence requirements,
and explicit task instructions take precedence over generic framework
guidance when they are more specific.

The framework's agents are defined in `.claude/agents/`. For non-trivial
work, run the session as the Orchestrator (`claude --agent orchestrator`)
or use a workflow command such as `/feature` or `/bug-fix`.

## Development Standards

### Purpose

These standards define the default expectations for AI-assisted software development.

Project-specific architecture, business rules, technology constraints, and conventions always take precedence when explicitly documented.

### Engineering Priorities

Apply priorities in this order:

1. Correctness
2. Preservation of intended business behavior
3. Data integrity
4. Security
5. Testability
6. Maintainability
7. Performance
8. Simplicity
9. Minimal scope of change

Do not sacrifice a higher-priority concern for a lower-priority one without explicitly identifying the tradeoff.

### Before Modifying Code

Before implementation:

- Understand the requirement.
- Inspect the relevant execution path.
- Search for existing implementations and patterns.
- Identify callers and downstream effects.
- Identify persistence/database effects.
- Identify external integrations affected.
- Identify relevant existing tests.
- Identify concurrency or transaction concerns when applicable.
- For migrated behavior, inspect the authoritative legacy implementation.

Do not begin implementation based only on filenames, class names, or assumptions.

### Implementation Principles

Prefer the smallest correct change.

Follow existing project patterns unless there is a concrete reason not to.

Do not introduce new abstractions solely because they appear cleaner.

Do not perform unrelated refactoring while implementing a feature or fixing a bug.

Do not silently change existing business behavior.

Do not remove validations, error handling, logging, or safeguards merely to make an implementation work.

Do not duplicate behavior already implemented elsewhere.

Prefer explicit, readable code over clever code.

Avoid unnecessary dependencies.

Respect existing architectural boundaries.

### Existing Code

Treat existing code as evidence, not automatically as correct.

When behavior is unclear:

1. inspect callers;
2. inspect tests;
3. inspect persistence behavior;
4. inspect documentation;
5. inspect legacy/reference implementation when applicable.

If ambiguity remains, report it rather than inventing business behavior.

### Error Handling

Do not hide failures.

Preserve useful diagnostic information.

Do not catch exceptions unless:

- recovery is possible;
- additional useful context is added; or
- the architecture requires translating the exception.

Avoid empty catch blocks and broad exception handling without justification.

### Logging

Logging should help diagnose real production behavior.

Do not log secrets or sensitive information.

Avoid excessive informational logging inside hot loops.

When useful, include identifiers that allow execution paths to be correlated.

### Database and Persistence

Before modifying persistence behavior, identify:

- tables/entities affected;
- reads;
- inserts;
- updates;
- deletes;
- transaction boundaries;
- retries;
- idempotency concerns;
- triggers or database-side behavior when relevant.

Never assume database schema changes are acceptable.

Do not create migrations or alter schemas unless explicitly required.

### Concurrency

When code may execute concurrently, evaluate:

- shared state;
- duplicate processing;
- race conditions;
- transaction isolation;
- idempotency;
- ordering requirements;
- retry behavior.

Do not introduce parallelism without evaluating thread safety and data consistency.

### Dependencies

Do not upgrade packages or frameworks as part of unrelated work.

Do not introduce a dependency when equivalent project functionality already exists.

### Generated Code

Do not manually modify generated code unless the project explicitly requires it.

Prefer changing the source or generator configuration.

### Completion

Implementation is not complete merely because it compiles.

Before declaring completion:

- build affected projects;
- run relevant tests;
- add or update tests for changed behavior;
- inspect the final diff;
- verify no unrelated files changed;
- identify unresolved risks or assumptions.

## Security Standards

### Purpose

Security must be considered during implementation and review without unnecessarily expanding task scope.

### Secrets

Never:

- hard-code passwords;
- hard-code API keys;
- commit tokens;
- expose connection credentials;
- log authentication secrets.

Use the project's approved configuration and secret-management mechanisms.

### Sensitive Data

Avoid logging:

- credentials;
- access tokens;
- session identifiers;
- private keys;
- payment information;
- sensitive personal information.

### Input

Treat external input as untrusted.

Evaluate:

- validation;
- encoding;
- injection;
- path traversal;
- unsafe deserialization;
- command execution;
- file upload risks.

### Authentication and Authorization

Authentication answers who the caller is.

Authorization answers what the caller may do.

Do not rely on UI restrictions as authorization.

Enforce authorization at appropriate backend boundaries.

### Database

Use parameterized queries or approved ORM patterns.

Do not construct SQL using untrusted string concatenation.

### External Calls

Validate assumptions about external responses.

Consider:

- timeout;
- failure;
- retry;
- authentication;
- certificate validation;
- unexpected payloads.

### Dependencies

Do not introduce dependencies with unnecessary privileges or capabilities.

Do not upgrade security-sensitive packages casually as part of unrelated tasks.

### Security Findings

Do not label theoretical issues as exploitable vulnerabilities without evidence.

Describe:

- attack/failure scenario;
- required preconditions;
- impact;
- recommended mitigation.

## Project Knowledge Standards

### Persistent Project Knowledge

Project-specific engineering knowledge is maintained under `.ai/`.

For non-trivial work, inspect relevant project knowledge before planning or modifying code.

Start with:

- `.ai/project.md`
- `.ai/architecture.md`

Then inspect only the knowledge relevant to the task:

- business behavior -> `.ai/business-rules/`
- component behavior -> `.ai/components/`
- persistence behavior -> `.ai/database/`
- external systems -> `.ai/integrations/`
- legacy behavior -> `.ai/legacy/`
- previous engineering decisions -> `.ai/decisions/`
- active or related work -> `.ai/tasks/`

Do not load unrelated project knowledge unnecessarily.

### Evidence

Project documentation provides context but may become outdated.

Source code, executable tests, database constraints, integration contracts, and observed behavior may provide stronger evidence.

When documentation materially conflicts with executable evidence:

1. identify the discrepancy;
2. investigate which behavior is authoritative;
3. report the discrepancy;
4. do not silently choose an interpretation.

Do not invent project-specific behavior when evidence is unavailable.

### Active Task Continuity

For significant work spanning multiple phases or sessions, use an active task document under `.ai/tasks/`.

Task documents may preserve:

- requirement or problem;
- relevant project knowledge;
- confirmed evidence;
- hypotheses;
- root cause;
- relevant files;
- implementation plan;
- implementation status;
- tests;
- review findings;
- unresolved questions;
- next steps;
- durable knowledge candidates.

Clearly distinguish confirmed evidence from hypotheses.

Task documents are working context and are not automatically authoritative business documentation.

### Knowledge Maintenance

At the completion of significant work, determine whether durable project knowledge was discovered or changed.

Examples include:

- confirmed business rules;
- persistence constraints;
- integration behavior;
- architectural decisions;
- intentional legacy differences;
- concurrency requirements;
- important operational constraints.

Update durable project knowledge only when sufficiently supported by evidence.

Do not convert debugging hypotheses, temporary observations, or speculation into permanent project documentation.

## Engineering Process and Human Control

### Engineering Workflow

For non-trivial work:

1. Understand the requirement.
2. Inspect relevant persistent project knowledge.
3. Investigate the existing implementation.
4. Identify root cause or expected design.
5. Plan the smallest correct change.
6. Implement.
7. Test adversarially.
8. Review independently.
9. Correct blocking findings.
10. Build and run relevant tests.
11. Inspect the final diff.
12. Identify any durable project-knowledge updates.

Do not skip investigation merely to reach implementation faster.

### Human Control

Do not perform consequential external or destructive actions without explicit authorization.

This includes:

- production deployment;
- destructive database operations;
- pushing commits;
- merging pull requests;
- production infrastructure changes;
- unrelated dependency upgrades;
- unrelated CI/CD modifications.

Compilation alone is not sufficient evidence that a task is complete.
